search_agent — how it works

A daily AI-news digest. Feeds in, one LangGraph run, a bulletin you read in the browser. It runs on one laptop: Docker + SQLite, no cloud step, about $2.50 a month.

RSS feeds

feedparser, 16 of them. ETag / 304, so a quiet feed costs nothing.

Tavily

news search, only for items still empty. Capped at 30 credits a day.

OpenAI · gpt-5.6-luna

Both LLM steps ask for a Pydantic model, not free text: a malformed answer fails as a validation error at the node that produced it, not as a KeyError three nodes later.

the clock — every 3 hours

APScheduler, inside the API process. It runs collect and stops there: no model, no cost.

DEMO_MODE winds no clock at all — a recording polls nothing.

a person — the press on /runs

The only paid action in the whole app. One click gets a question, not a run; only the answer is a POST. You pick the model and the output language there.

LangGraph StateGraph · no checkpointer

collect

poll every feed, keep what is new. A 404 is that source's failure, not the run's.

→

dedupe

one story filed by five outlets is one story. Fuzzy title match; the loser is marked, never deleted.

→

enrich

give thin items a body, cheapest tier first: the feed's own HTML, then a fetch, then one Tavily credit.

→

summarize · Send ×N

one branch per article, 10 in flight. Each branch commits its own summary row before it returns.

→

rank ×3

the only step that sees the whole day, read three times shuffled and aggregated by Borda count. How far the three agreed ships on the bulletin.

→

persist

publishes the day as a new version, not a second entry; runs the free checks over what it published; closes the run.

every node writes its own run_steps row as it runs  ·  nothing new today? the graph skips straight to persist and the run still closes

SQLite · data/app.db · WAL, FTS5

sources · articles · summaries · bulletins · bulletin_items · runs · run_steps · verdicts · eval_results

The graph state carries ids, not bodies — bodies stay here, which is what keeps a hundred parallel branches cheap.

There is no checkpoint file. A summary belongs to its article and is committed by the branch that paid for it, so a run that dies loses the ranking and nothing else; the next press ranks what is already here.

An example run — pressed at 16:06, bulletin in Turkish

collect     16 feeds polled    1214 items seen  ->  31 new
dedupe      31 candidates                      ->  24            "OpenAI ships GPT-5.6 Luna" = "GPT-5.6 Luna is here": 3 URLs, 1 story
enrich      24 examined                        ->  22 with a body   18 from the feed's own HTML, 3 fetched, 1 Tavily credit
summarize   24 branches, 10 at a time          ->  24 rows, each committed by the branch that bought it
rank        24 summaries, read 3 times         ->  the day in order + a note, with the readings' agreement on the bulletin
persist     1 bulletin v1, its items, 6 run_steps  ->  about $0.03 — a month of pressing this is $2-3

Then you open /, read it, and mark one summary wrong and say why; that verdict goes to the verdicts table. /runs/<id> shows those six lines again with their tokens, their cost, how long each one took, and what the checks made of the result. Nothing above happens on its own: the clock only polls feeds, and the bulletin waits for a press.

quality/ and evals/ — the free half and the paid half

src/ainews/quality/ is product code. The deterministic checks call no model and write no row, so persist runs them and /runs/<id> draws them.

src/ainews/evals/ is the half that spends. It is imported by neither the pipeline nor the web layer — only by cli.py, so the app still has exactly one button that spends money.

  • pytest, offline, over a recorded fixture
  • the reader's right / wrong, and which claim failed
  • a sampled grounding judge, uncalibrated until thirty labels a class
  • rank stability: min(τ, chance-corrected Jaccard), gate 0.6
  • two prompts over the same frozen bodies
